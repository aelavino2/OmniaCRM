# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Источник правды

`docs/tz.md` — техническое задание, собранное по итогам обсуждений с командой. **Читай его перед любой задачей, затрагивающей архитектуру, доменную модель или API.** Этот файл не пересказывает ТЗ, а фиксирует то, что нужно знать до его чтения.

`README.md` — публичное описание проекта, более общее и рассчитанное на внешнего читателя. При расхождении с ТЗ прав ТЗ.

### Статусы требований в ТЗ — читай их буквально

Каждое требование ТЗ пронумеровано (`ТР-<раздел>.<номер>`) и имеет один из трёх статусов. Статус определяет, что тебе можно делать:

| Статус | Что значит | Как действовать |
|---|---|---|
| **УТВЕРЖДЕНО** | Решено командой | Считай ограничением. Нарушать нельзя, предлагать пересмотр — только явно и отдельно |
| **НА СОГЛАСОВАНИИ** | Предложение, командой **не подтверждено** | Не выдавай за решённое и не закладывай в код как данность. Если задача упирается в такой пункт — спроси |
| **НЕ ОПРЕДЕЛЕНО** | Открытый вопрос, ответа нет | Не придумывай ответ. Назови вопрос и спроси. Полный перечень — раздел 17 ТЗ, обозначения `ОВ-<номер>` |

Самая частая ошибка здесь — принять НА СОГЛАСОВАНИИ за УТВЕРЖДЕНО. RabbitMQ (ТР-13.2, ТР-15.6), монорепо (ТР-15.7), Docker Compose (ТР-15.8), OpenAPI и `.proto` до кода (ТР-15.9), CI (ТР-15.10), хостинг (ТР-15.11) — это предложения, а не принятые решения.

Ссылайся на требования по идентификатору, а не по номеру раздела: разделы при пересмотре ТЗ сдвигаются, идентификатор закреплён за требованием навсегда.

## Состояние репозитория

Кода нет. Есть README, ТЗ и конфигурация Claude Code. `OmniaCRM/src/Main.java` — нетронутый шаблон IntelliJ («Hello and welcome!»), к проекту отношения не имеет. Системы сборки, зависимостей, тестов и слоёв приложения не существует.

Практическое следствие: почти любая задача — создание чего-то впервые, а не правка существующего. Не ищи модуль-образец или сложившуюся конвенцию, их нет. Уточняющий вопрос звучит не «где это лежит», а «как мы это решаем».

## Команды

Сборки нет. Шаблон запускается однофайловым режимом JDK:

```
java OmniaCRM/src/Main.java
```

Установлен JDK 25 (LTS), language level проекта — 25.

**Когда появится Gradle-сборка — заменить этот раздел реальными командами (сборка, прогон тестов, прогон одного теста) в том же коммите, который добавляет сборку.** Система сборки выбрана — **Gradle** (ТР-15.2, УТВЕРЖДЕНО). Но самой сборки в репозитории ещё нет: ни `settings.gradle(.kts)`, ни `build.gradle(.kts)`, ни wrapper’а. Пока они не появились, не выдумывай команды и не предполагай, что `gradle`/`./gradlew` здесь работают (глобальный `gradle` в PATH не установлен).

## Инварианты архитектуры

Раздел 5 ТЗ, все требования со статусом УТВЕРЖДЕНО — их дёшево заложить сразу и дорого добавить потом. Код, который их нарушает, неверен независимо от того, работает ли он:

1. **ТР-5.1 — `tenant_id` в каждой таблице с первого дня**, даже пока тенант в проде один. Не «добавим, когда появится второй клиент».
2. **ТР-5.2 — `Case` без хардкода полей под конкретный бизнес.** Гибкая схема — типизированный JSONB в Postgres, валидация на уровне приложения под каждый тип дела. Не заводи отдельные таблицы или колонки под барбершоп, тур или маркетплейс.
3. **ТР-5.3 — версионирование API сразу**: `/api/v1/...`.
4. **ТР-5.4 — создание заявки идемпотентно с первого дня.** Повторный запрос клиента не создаёт дубликат.
5. **ТР-5.5 — REST наружу, gRPC внутрь.** Сайты, боты, мобильные клиенты и дашборд ходят по HTTP/REST; сервисы ядра между собой — по gRPC. Мобильный клиент — именно HTTP, не gRPC.

Стек: Spring Boot, PostgreSQL, Gradle.

### Java и Kotlin — ADR-0001

Язык выбирается на **весь модуль** (ТР-15.1, `docs/adr/0001-java-kotlin-split-by-module.md`):

| Модуль | Язык | Ревью / сборка |
|---|---|---|
| `core` — Tenant, Client, Case, Catalog, Tracking, Outbox | Java | `java-reviewer` / `java-build-resolver` |
| `payment`, `notification`, `telegram-bot` | Kotlin | `kotlin-reviewer` / `kotlin-build-resolver` |
| `contracts` — OpenAPI, `.proto` | без языка | — |

- Не клади `.java` в Kotlin-модуль и `.kt` в Java-модуль, включая тесты.
- Модули не делят код: только сгенерированный из `contracts`, остальное — по сети (REST, gRPC).
- Kotlin-модуль: `kotlin("plugin.spring")`, `jvmToolchain(25)`, при JPA — `kotlin("plugin.jpa")`. `data class` не используется как JPA-сущность.
- Скрипты сборки — Kotlin DSL (`*.gradle.kts`) везде.

## Состав системы

Ядро (`Tenant`, `Client`, `Case`) — единый модуль с одной транзакционной БД. Распределённые транзакции на этом масштабе не окупаются.

Выносятся в отдельные сервисы: **Payment** (свой периметр безопасности, идемпотентность вебхуков провайдера), **Notification** (асинхронный, зависит от нестабильных внешних API), **Telegram-бот** (по сути обычный HTTP-клиент API ядра).

Отложено до реальной необходимости: Reporting/Analytics, отдельный диспетчер исходящих вебхуков (начинается как таблица `outbox` + фоновый воркер внутри монолита), Auth/Billing как отдельный сервис.

Полная доменная модель — ТР-6.1, компоненты — ТР-7.1 — ТР-7.3.

## Чего не делать

- **Не разделять сервисы по типу бизнеса** (`barber-service`, `designer-service` и подобное). Это воспроизводит ровно ту проблему, ради которой затевалось единое ядро. Разница между бизнесами живёт в данных — тип `Case` плюс JSON-схема, — а не в инфраструктуре. В ТЗ это ТР-7.4 со статусом **НА СОГЛАСОВАНИИ**: запрет сформулирован, но командой не подтверждён. Считай его действующим по умолчанию, а если задача требует его нарушить — не нарушай молча, а вынеси на обсуждение.
- **Не придумывать ответы на НЕ ОПРЕДЕЛЕНО.** В разделе 17 ТЗ десять открытых вопросов (ОВ-1 — ОВ-10): хостинг, домены клиентских сайтов, бухучёт, редактирование Company Profile, модель монетизации, аудитория мобильного интерфейса, срок первого заказчика, доступ к коду подключаемых сайтов, переход к инициации платежа, шина доменных событий. Если задача упирается в один из них — назови его по идентификатору и спроси.
- **Не превращать НА СОГЛАСОВАНИИ в факт** молча. См. таблицу статусов выше.

## Git

- `main` — опубликованная ветка, соответствует GitHub.
- `development` — рабочая ветка, разработка идёт здесь.
- Push и коммиты — только по явной просьбе.
- Ветка под задачу называется `<номер issue>-<кратко-латиницей>`, например `1-build-system-gradle`. PR идёт в `development`.
- `Closes #N` в описании PR закрывает issue автоматически, только если PR направлен в ветку по умолчанию (`main`). У PR в `development` issue привязывается вручную: в блоке Development справа на странице PR или issue.
- Не переименовывай ветку, у которой есть открытый PR: GitHub закроет этот PR, и открыть его заново будет нельзя.

Файлы IDE (`.idea/`, `*.iml`) уже дважды попадали в историю и вычищались. Они закрыты корневым `.gitignore` — не добавляй их обратно и не коммить через `git add -f`.

`gh` CLI установлен и авторизован (аккаунт `aelavino2`, scope `repo`), issues в репозитории включены.

Слэш-команд проекта нет: `commands/` пуста намеренно. Хуков тоже нет. Встроенные команды Claude Code доступны всегда: `/code-review`, `/security-review`, `/simplify`, `/init`.

### Агенты (`.claude/agents/`)

| Агент | Приоритет | Когда вызывать |
|---|---|---|
| `java-build-resolver` | **Высокий** | Падает Gradle-сборка или компиляция Java. Первый кандидат при заведении сборки (issue #2) |
| `database-reviewer` | **Высокий** | Любая миграция или схема: ядро, `tenant_id`, JSONB для `Case` (issue #3) |
| `java-reviewer` | **Высокий** | Ревью Java/Spring Boot кода перед PR |
| `security-reviewer` | **Высокий** — для Payment | Код, который принимает внешний ввод: REST-эндпоинты, вебхуки платёжного провайдера, аутентификация |
| `kotlin-reviewer` | **Высокий** | Ревью Kotlin-сервисов (`payment`, `notification`, `telegram-bot`) перед PR. Проверяет правила ADR-0001 и идемпотентность вебхуков |
| `kotlin-build-resolver` | **Высокий** | Падает сборка или компиляция Kotlin-модуля |

Агенты вызываются явно, сами по себе не запускаются. Каждый стартует с чистым контекстом — не гоняй их на мелкие правки. Встроенные агенты: `Explore` — поиск по кодовой базе, `Plan` — план реализации.
