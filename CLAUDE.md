# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Источник правды

`docs/terms-of-reference.md` — техническое задание, собранное по итогам обсуждений с командой. **Читай его перед любой задачей, затрагивающей архитектуру, доменную модель или API.** Этот файл не пересказывает ТЗ, а фиксирует то, что нужно знать до его чтения.

`README.md` — публичное описание проекта, более общее и рассчитанное на внешнего читателя. При расхождении с ТЗ прав ТЗ.

### Статусы требований в ТЗ — читай их буквально

Каждое требование ТЗ пронумеровано (`REQ-<раздел>.<номер>`) и имеет один из трёх статусов. Статус определяет, что тебе можно делать:

| Статус | Что значит | Как действовать |
|---|---|---|
| **УТВЕРЖДЕНО** | Решено командой | Считай ограничением. Нарушать нельзя, предлагать пересмотр — только явно и отдельно |
| **НА СОГЛАСОВАНИИ** | Предложение, командой **не подтверждено** | Не выдавай за решённое и не закладывай в код как данность. Если задача упирается в такой пункт — спроси |
| **НЕ ОПРЕДЕЛЕНО** | Открытый вопрос, ответа нет | Не придумывай ответ. Назови вопрос и спроси. Полный перечень — раздел 17 ТЗ, обозначения `OQ-<номер>` |

Самая частая ошибка здесь — принять НА СОГЛАСОВАНИИ за УТВЕРЖДЕНО. На 23.09.2026 утверждены RabbitMQ с outbox, монорепо, Docker Compose, контракты до кода и CI на GitHub Actions (REQ-13.1, REQ-13.2, REQ-15.6 — REQ-15.10). Хостинг (REQ-15.11) не определён. Архитектурные решения с обоснованием — `docs/adr/`.

Ссылайся на требования по идентификатору, а не по номеру раздела: разделы при пересмотре ТЗ сдвигаются, идентификатор закреплён за требованием навсегда.

## Состояние репозитория

Кода нет. Есть README, ТЗ, конфигурация Claude Code и корень Gradle-сборки без модулей: wrapper, `settings.gradle.kts` и `build-logic/` с convention-плагином `omnia.java-conventions` (Java toolchain 25). Root `build.gradle.kts` нет намеренно: общие настройки модулей живут в `build-logic/`, модуль подключает их через `plugins { id("omnia.java-conventions") }`. `OmniaCRM/src/Main.java` — нетронутый шаблон IntelliJ («Hello and welcome!»), к проекту отношения не имеет.

Практическое следствие: почти любая задача — создание чего-то впервые, а не правка существующего. Не ищи модуль-образец или сложившуюся конвенцию, их нет. Уточняющий вопрос звучит не «где это лежит», а «как мы это решаем».

## Команды

Сборка — только через wrapper, глобальный Gradle не нужен (на Windows — `gradlew.bat`):

```
./gradlew help                                          # проверить, что сборка конфигурируется
./gradlew build                                         # собрать и прогнать тесты всех модулей
./gradlew :<module>:test                                # тесты одного модуля
./gradlew :<module>:test --tests '<пакет.КлассTest>'    # один тестовый класс
```

Пока модулей нет, задач `build` и `test` в корне не существует: `./gradlew build` по сокращению имени запускает `buildEnvironment`. Реальными эти команды станут с первым модулем.

Шаблон IntelliJ запускается однофайловым режимом JDK: `java OmniaCRM/src/Main.java`.

Установлен JDK 25 (LTS), language level проекта — 25.

## Кто работает с системой

Напрямую с CRM работают **только владельцы бизнеса и их сотрудники** (REQ-4.4, REQ-11.4): входят из админ-панели своего сайта, у бизнеса может быть несколько пользователей. Клиенты бизнеса доступа к CRM не имеют. Их заявки приходят только с подключённого сайта или из Telegram-бота, обмен односторонний, контакт клиента обязателен (REQ-8.5, REQ-8.6). Сайты бизнеса могут быть на любом стеке (PHP, C#…) — интеграция только через HTTP-контракт (REQ-8.4). Подключение и настройку бизнеса делают разработчики (REQ-8.8).

Деньги через CRM не проходят, платежи она не инициирует (REQ-9.1, REQ-9.3). Она только **собирает данные об оплатах**: от сайта, из банка бизнеса или ручной отметкой (REQ-9.2) — для статистики дохода (REQ-11.9).

## Инварианты архитектуры

Раздел 5 ТЗ, все требования со статусом УТВЕРЖДЕНО — их дёшево заложить сразу и дорого добавить потом. Код, который их нарушает, неверен независимо от того, работает ли он:

1. **REQ-5.1 — `tenant_id` в каждой таблице с первого дня**, даже пока тенант в проде один. Не «добавим, когда появится второй клиент».
2. **REQ-5.2 — `Case` без хардкода полей под конкретный бизнес.** Гибкая схема — типизированный JSONB в Postgres, валидация на уровне приложения под каждый тип дела. Не заводи отдельные таблицы или колонки под барбершоп, тур или маркетплейс.
3. **REQ-5.3 — версионирование API сразу**: `/api/v1/...`.
4. **REQ-5.4 — создание заявки идемпотентно с первого дня.** Повторный запрос клиента не создаёт дубликат.
5. **REQ-5.5 — REST наружу, gRPC внутрь.** Сайты, боты, веб- и мобильный интерфейс владельца бизнеса ходят по HTTP/REST; сервисы ядра между собой — по gRPC. Мобильный клиент — именно HTTP, не gRPC.

Стек: Spring Boot, PostgreSQL, Gradle.

### Java и Kotlin — ADR-0001

Язык выбирается на **весь модуль** (REQ-15.1, `docs/adr/0001-java-kotlin-split-by-module.md`):

| Модуль | Язык | Ревью / сборка |
|---|---|---|
| `core` — Tenant, Client, Case, Catalog, Outbox, интерфейс владельца, статистика | Java | `java-reviewer` / `java-build-resolver` |
| `payment`, `notification`, `telegram-bot` | Kotlin | `kotlin-reviewer` / `kotlin-build-resolver` |
| `mobile-app` — приложение владельца (ADR-0006) | Kotlin | `kotlin-build-resolver`; ревьюера под Android пока нет |
| `contracts` — OpenAPI, `.proto` | без языка | — |

- Не клади `.java` в Kotlin-модуль и `.kt` в Java-модуль, включая тесты.
- Модули не делят код: только сгенерированный из `contracts`, остальное — по сети (REST, gRPC).
- Kotlin-модуль: `kotlin("plugin.spring")`, `jvmToolchain(25)`, при JPA — `kotlin("plugin.jpa")`. `data class` не используется как JPA-сущность.
- Скрипты сборки — Kotlin DSL (`*.gradle.kts`) везде.

## Состав системы

Ядро (`Tenant`, `Client`, `Case`) — единый модуль с одной транзакционной БД. Распределённые транзакции на этом масштабе не окупаются.

Выносятся в отдельные сервисы: **Payment** (свой периметр безопасности, идемпотентность вебхуков провайдера), **Notification** (асинхронный, зависит от нестабильных внешних API), **Telegram-бот** (по сути обычный HTTP-клиент API ядра).

Отложено до реальной необходимости: Reporting/Analytics, отдельный диспетчер исходящих вебхуков (начинается как таблица `outbox` + фоновый воркер внутри монолита), Auth/Billing как отдельный сервис.

Полная доменная модель — REQ-6.1, компоненты — REQ-7.1 — REQ-7.3.

## Чего не делать

- **Не разделять сервисы по типу бизнеса** (`barber-service`, `designer-service` и подобное). Это воспроизводит ровно ту проблему, ради которой затевалось единое ядро. Разница между бизнесами живёт в данных — тип `Case` плюс JSON-схема, — а не в инфраструктуре. В ТЗ это REQ-7.4 со статусом **НА СОГЛАСОВАНИИ**: запрет сформулирован, но командой не подтверждён. Считай его действующим по умолчанию, а если задача требует его нарушить — не нарушай молча, а вынеси на обсуждение.
- **Не придумывать ответы на НЕ ОПРЕДЕЛЕНО.** Открытые вопросы — раздел 17 ТЗ: хостинг (OQ-1), домены сайтов (OQ-2), монетизация (OQ-5), срок первого заказчика (OQ-7), доступ к коду сайтов (OQ-8), шина событий (OQ-10), данные об оплатах из банка (OQ-11), канал «на телефон» (OQ-13), платформы мобильного приложения (OQ-15). OQ-3, OQ-4, OQ-6, OQ-9, OQ-12, OQ-14 закрыты. Если задача упирается в один из них — назови его по идентификатору и спроси.
- **Не превращать НА СОГЛАСОВАНИИ в факт** молча. См. таблицу статусов выше.

## Git

- `main` — опубликованная ветка, соответствует GitHub.
- `development` — рабочая ветка, разработка идёт здесь.
- Push и коммиты — только по явной просьбе.
- Ветка под задачу называется `<номер issue>-<кратко-латиницей>`, например `1-build-system-gradle`. PR идёт в `development`.
- `Closes #N` в описании PR закрывает issue автоматически, только если PR направлен в ветку по умолчанию (`main`). У PR в `development` issue привязывается вручную: в блоке Development справа на странице PR или issue.
- Не переименовывай ветку, у которой есть открытый PR: GitHub закроет этот PR, и открыть его заново будет нельзя.
- Issues пишутся по шаблону `.github/ISSUE_TEMPLATE/task.md`: на английском, связным текстом, разделы Context, Goal, Done when. Ссылки на ТЗ — по якорю и на ветку `development` (`…/blob/development/docs/terms-of-reference.md#req-15-7`): ветки задач удаляются после слияния, и ссылки на них ломаются. Мелкие шаги — отдельные sub-issues.

Файлы IDE (`.idea/`, `*.iml`) уже дважды попадали в историю и вычищались. Они закрыты корневым `.gitignore` — не добавляй их обратно и не коммить через `git add -f`.

`gh` CLI установлен и авторизован (аккаунт `aelavino2`, scope `repo`), issues в репозитории включены.

## Агенты, навыки и команды

Лежат в `.claude/`. Устройство каталога описано в `.claude/README.md`, происхождение — в `.claude/skills/THIRD-PARTY.md`. Все агенты и навыки перенесены из ECC. Пять агентов адаптированы под стек и проверяют инварианты раздела 5 ТЗ. **Навыки остались общего назначения и ТЗ не знают**: если их совет противоречит ТЗ или этому файлу, прав ТЗ. Порог покрытия тестами командой не утверждён — не вводи его сам.

Слэш-команд проекта нет: `commands/` пуста намеренно. Хуков тоже нет. Встроенные команды Claude Code доступны всегда: `/code-review`, `/security-review`, `/simplify`, `/init`.

### Агенты (`.claude/agents/`)

| Агент | Приоритет | Когда вызывать |
|---|---|---|
| `java-build-resolver` | **Высокий** | Падает Gradle-сборка или компиляция Java. Первый кандидат при заведении сборки (issue #2) |
| `database-reviewer` | **Высокий** | Любая миграция или схема: ядро, `tenant_id`, JSONB для `Case` (issue #3) |
| `java-reviewer` | **Высокий** | Ревью Java/Spring Boot кода перед PR |
| `security-reviewer` | **Высокий** — для Payment | Код, который принимает внешний ввод: REST-эндпоинты, вебхуки платёжного провайдера, аутентификация |
| `kotlin-reviewer` | **Высокий** | Ревью Kotlin-сервисов (`payment`, `notification`, `telegram-bot`) перед PR. Проверяет правила ADR-0001 и идемпотентность вебхуков |
| `kotlin-build-resolver` | **Высокий** | Падает сборка или компиляция Kotlin-модуля |

Агенты вызываются явно, сами по себе не запускаются. Каждый стартует с чистым контекстом — не гоняй их на мелкие правки. Встроенные агенты: `Explore` — поиск по кодовой базе, `Plan` — план реализации.
