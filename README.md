# Универсальное CRM-ядро (рабочее название)

Пет-проект на **Java / Kotlin**: единое серверное ядро (backend-сервис), к которому по API обращаются разные собственные сайты и проекты, чтобы не дублировать одну и ту же логику (пользователи, заказы/заявки, статистика) в каждом новом проекте.

> Статус: идея на стадии проектирования. Документ фиксирует всё, что обсуждалось, чтобы не потерять контекст между сессиями работы над проектом.

---

## 1. Суть идеи

Единый бэкенд ("ядро"), который:

- хранит пользователей, заявки/заказы/записи и события;
- отдаёт и принимает данные через API;
- переиспользуется во всех будущих сайтах автора, вместо того чтобы каждый раз писать похожую логику заново.

Примеры сайтов, которые должны подключаться к ядру: рекламный сайт барбера, сайт магазина очков, сайт для приёма заявок дизайнеров мебели/интерьера, сайт для дизайнеров/конструкторов одежды.

## 2. Обязательные требования (зафиксировано)

- **Интеграция с Telegram-ботами.** Клиент нажимает в боте "хочу купить/записаться" → заявка уходит в ядро → сохраняется в БД, возможен ответ/уведомление обратно.
- **Возможность подключения к разным сайтам и проектам.** Не привязываться к одному фронтенду — ядро должно быть переиспользуемым.
- **Модель интеграции — server-to-server (S2S).** Не виджет на стороне браузера пользователя, а бэкенд сайта-клиента сам обращается к API ядра по закрытому ключу/токену (как классическая server-side интеграция, а не публичный OAuth-флоу для конечных пользователей).

## 3. Важные принятые решения (чтобы не переспрашивать себя же позже)

- **Мультитенантность ≠ распределённая БД.** Изоляция данных разных "клиентов" ядра решается через `tenant_id` (или отдельные схемы), а не через физически распределённую БД (шардирование/репликация нужны только при реальной высокой нагрузке, которой пока нет и не будет на старте).
- **Не гнаться за "высоконагруженностью" с первого дня.** Это преждевременная оптимизация без единого реального пользователя. Архитектуру усложняем по мере роста, а не заранее.
- **Данные — гибкие, не жёсткая схема под одну нишу.** У барбера (запись на время), магазина (заказ товара) и дизайнера (заявка/бриф) разные предметные области. Подход — не единая жёсткая таблица `Order`, а универсальная сущность с типом и гибкими полями (EAV/JSONB), плюс общий журнал событий.
- **Модель развивается от частного к общему.** Сначала — под один свой реальный сайт, только при столкновении со вторым непохожим случаем — обобщаем модель. Не пытаться заранее угадать универсальную схему под все ниши сразу (паралич анализа).

## 4. Архитектурная концепция (черновая, для дальнейшей проработки)

Базовые сущности ядра:

- **Contact / Lead** — клиент (имя, телефон, telegram_id, источник).
- **Entity** — универсальная "заявка" с типом (`booking | order | inquiry`) и произвольными полями.
- **Event** — журнал событий (создано, статус изменился, оплачено) — основа для уведомлений в Telegram и для будущей статистики/аналитики.
- **Integration / Webhook** — у каждого сайта-клиента свой API-ключ; ядро умеет как принимать вызовы (REST API), так и само слать вебхуки обратно (события → уведомления).

Два канала связи, как у крупных CRM (amoCRM, Bitrix24):

- **REST API** — когда сайт/бот сам инициирует действие в ядре (создать заявку, обновить статус).
- **Webhooks** — когда ядро само оповещает внешний сервис о произошедшем событии. Важно сразу закладывать идемпотентную обработку на стороне получателя (повторные/задвоенные вебхуки — обычное явление даже у крупных CRM).

## 5. Технологический стек (ориентир)

- Java / Kotlin, Spring Boot (или Ktor)
- PostgreSQL (JSONB — под гибкие поля сущностей)
- Flyway — миграции
- Auth: API-ключи / client credentials для server-to-server вызовов; опционально Keycloak — ради практики
- Очереди (опционально, для практики событийной модели): RabbitMQ

## 6. Roadmap / этапы развития

| Этап | Что делаем | Ориентир по времени |
|---|---|---|
| 0. Ядро-практика | Одно приложение без мультитенантности, 2–3 собственных сайта как единственные клиенты. Цель — рабочий цикл сайт → API → БД → уведомление | 2–4 месяца в свободное время |
| 1. MVP как продукт | Добавляется `tenant_id`, базовая статистика (продажи/записи/пользователи по клиенту), простая админка. Можно показывать пилотным знакомым бизнесам бесплатно | + полгода–год |
| 2. Продаваемый продукт | Биллинг, тарифные лимиты, онбординг без личного участия, документация API | от года |
| 3. Рост | Больше вертикалей, тонкая аналитика, возможен маркетплейс интеграций, партнёрская сеть внедренцев | далее |

Идея не становится бизнесом сразу — сначала пет-проект и личное использование, коммерциализация — опциональный поздний этап, если система "выстрелит" на собственных сайтах.

## 7. Аналоги на рынке

- **amoCRM** — лидер СНГ-рынка малого/среднего бизнеса, только платные тарифы, REST API v4 с OAuth2 и вебхуками входит в подписку. Официальные партнёры есть и в Бишкеке.
- **Bitrix24** — есть бесплатный тариф для базовой командной работы, но по состоянию на 2026 год полноценный REST API требует платного тарифа плюс отдельной подписки на Маркетплейс (условия могли снова измениться — проверять на момент реальной интеграции).
- **RetailCRM (Simla)** — ближайший концептуальный аналог: CRM, спроектированная вокруг заказа/доставки/повторной покупки, с готовым Message Gateway / Bot API / Transport API для чатов и ботов.
- Локально в Кыргызстане своих крупных CRM-платформ нет — рынок закрывают интеграторы (Aunimeda, iprofi.kg, CRM Technologies, Yoda и др.), которые внедряют и кастомизируют amoCRM/Bitrix24, а не пишут собственные продукты с нуля.

## 8. Возможная ниша/отличие от крупных игроков

Крупные CRM заточены под sales-pipeline (воронка продаж, B2B). Отличие может строиться на **сервисных и творческих малых бизнесах**: запись на приём/консультацию + статистика загрузки (мастер, дизайнер), а не общая "воронка сделок". Это ближе к реальным потребностям барбера/дизайнера, чем стандартный sales-pipeline.

## 9. Варианты названия (черновые, не выбрано)

- Смысловые (связь/ядро): Nexo, Nexa, Corvo, Linko, Uniqore
- Смысловые (универсальность): Anyra, Omnia, Flexo
- Нейтральные короткие: Kelo, Vezo, Doro, Naru

При выборе — проверить домен/товарный знак, не звучать слишком похоже на "CRM" в лоб (amoCRM/RetailCRM уже заняли этот паттерн).

## 10. Возможная тема для магистерской диссертации

Идею стоит обернуть вокруг архитектурного/исследовательского вопроса, а не просто "ещё одна CRM":

- Разработка универсальной модели данных для интеграции разнородных клиентских приложений через единый серверный API (акцент на EAV/JSONB против жёсткой схемы, сравнительный анализ).
- Событийно-ориентированная архитектура интеграции backend-сервисов на примере CRM-ядра (акцент на webhooks/events, идемпотентность, сравнение с существующими решениями).
