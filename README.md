## Зачем этот проект

Разные сайты (услуги, e-commerce, лендинги с заявками) регулярно требуют одного и того же: регистрацию пользователей, приём заявок, хранение заказов, уведомления клиенту. OmniaCRM выносит эту логику в **единое CRM-ядро**, к которому подключаются сайты и Telegram-боты как клиенты через API. Вместо того чтобы каждый новый проект заново реализовывал одну и ту же логику работы с клиентами и заявками, она реализуется один раз в ядре и переиспользуется.

> 🚧 **Статус:** идея и черновой набросок направления. Архитектура и доменная модель ещё не спроектированы — всё ниже может измениться. Кода нет.

## Как это должно работать

Ключевая сложность в том, что у разных проектов совершенно разные бизнес-процессы: у барбершопа — запись на время, у магазина — заказ товара, у дизайнера — заявка на консультацию. Поэтому ядро не должно быть жёстко заточено под один тип сущности — оно должно уметь гибко описывать разные типы "дел" (запись, заказ, заявка), не требуя переделки схемы под каждый новый проект.

Сайты и боты выступают клиентами этого ядра: отправляют в него события (новую заявку, заказ, регистрацию), получают из него данные и уведомления обратно. Как именно это будет устроено на уровне API и хранения данных — предстоит спроектировать.

## Что должно уметь ядро

На уровне идеи, а не архитектуры:

- Принимать заявки/заказы/записи с разных сайтов и ботов по общему контракту
- Хранить контакты клиентов и историю их обращений
- Поддерживать несколько независимых проектов на одном ядре, не смешивая их данные
- Уведомлять сайт-клиент о том, что что-то изменилось (новый статус, оплата и т.д.)
- Достаточно гибко описывать разные типы сущностей, чтобы не переписывать схему под каждый новый бизнес

## Стек

Backend на Kotlin/Java, поверх Spring Boot, с PostgreSQL в качестве хранилища. Интеграция с Telegram Bot API и REST/webhooks для сайтов-клиентов. Конкретные версии и детали пока не фиксирую — это решится на этапе проектирования.
