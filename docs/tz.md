# Техническое задание (черновик) — универсальное CRM-ядро (OmniaCRM)

> Статус: рабочий черновик по итогам обсуждения с командой. Часть пунктов — согласованные решения, часть — открытые вопросы, часть — рекомендации, требующие явного подтверждения командой. Разметка ниже:
> ✅ — решено командой · ⚠️ — рекомендация, нужно обсудить и подтвердить/отклонить · ❓ — открытый вопрос, ответа пока нет

## 1. Цель и контекст проекта

Единое CRM-ядро, к которому подключаются сайты, Telegram-боты и мобильные клиенты разных бизнесов (барбершоп, дизайнер интерьеров, тур-сайт с оплатой, маркетплейс женских изделий) как клиенты через API. Логика работы с клиентами, заявками/заказами и уведомлениями реализуется один раз в ядре и переиспользуется вместо повторной реализации под каждый новый проект.

- ✅ Статус проекта на данный момент: pet-проект с целью перехода на продажи (не финансируется извне, нет внешнего дедлайна от инвестора).
- ✅ Мотивация текущей разработки: подготовить систему заранее, чтобы при появлении реального заказчика (из уже заинтересованных: барбер, дизайнер, тур-сайт, маркетплейс) подключить его в короткие сроки.
- ✅ Команда: 2 backend-разработчика уровня middle (включая автора идеи), frontend — по модели "вайбкодинг" (быстрая разработка с помощью AI-инструментов, без выделенного frontend-инженера).

## 2. Границы охвата (что должно работать)

- ✅ Ядро должно закрывать **все 4 бизнес-кейса**: барбершоп (запись), дизайнер интерьеров (заявка на консультацию), тур-сайт (бронирование + оплата), маркетплейс женских изделий (заказ товара + оплата).
- ✅ Ядро должно поддерживать **все 3 способа подключения клиента**: старый сайт без изменений в коде, Telegram-бот, новый сайт, изначально спроектированный под контракт ядра.
- ⚠️ **Рекомендация по порядку реализации** (см. раздел 15) — построить и проверить работу ядра сначала на одной вертикали (маркетплейс), затем на второй, структурно другой (барбер), прежде чем считать абстракцию проверенной. Формальная цель "закрыть все 4" не отменяется, но должна достигаться поэтапно, а не параллельной стройкой по всем направлениям одновременно.

## 3. Доменная модель ядра

Общие сущности, вынесенные из анализа всех 4 кейсов:

| Сущность | Назначение | Комментарий |
|---|---|---|
| **Tenant / Project** | Контейнер, разделяющий данные разных бизнесов | Обязателен с первого дня, даже при одном тенанте |
| **Client** | Контакты клиента бизнеса и история обращений | Общий для всех кейсов |
| **Case / Order** | Гибкая сущность "дела": запись, заявка, заказ, бронь | ✅ Без хардкода полей под конкретный бизнес — гибкая схема (см. п.4) |
| **Payment** | Факт и статус оплаты | ✅ Опциональный модуль — есть не у всех кейсов (барбер/дизайнер могут быть без него) |
| **Product / Service** | Товар или услуга (каталог) | Нужен там, где есть каталог (маркетплейс, тур) |
| **Status / Workflow** | Состояние дела и переходы между статусами | ✅ На старте фиксированный enum допустим, если смена набора статусов в будущем остаётся дешёвой |
| **Notification** | Уведомление клиенту и/или бизнесу | Email/Telegram на старте (см. п.8) |
| **Company Profile** | Динамические данные бизнеса (адрес, контакты, лого, часы работы) | ❓ Не решено: кто редактирует (личный кабинет бизнеса или вручную при внедрении) |

## 4. Архитектурные принципы, зафиксированные с первого дня

Эти решения дёшево заложить сейчас и дорого добавлять позже — согласованы независимо от объёма MVP:

- ✅ **Мультитенантность**: `tenant_id` в каждой таблице с первого дня, даже при одном тенанте в проде.
- ✅ **Гибкость `Case`**: без хардкода полей под конкретный бизнес — типизированное JSON-поле (JSONB в Postgres) с валидацией на уровне приложения под каждый тип дела.
- ✅ **Контракт API**: версионирование сразу (`/api/v1/...`), создание заявки — идемпотентная операция с первого дня (повторный запрос от клиента не создаёт дубликат).
- ✅ **Разделение внешнего и внутреннего протокола**: наружу (сайты, боты, мобильные клиенты, дашборд) — HTTP/REST; между внутренними сервисами ядра — gRPC.

## 5. Компонентная архитектура

Ядро (`Client`, `Case`, `Tenant`) остаётся единым модулем/сервисом с одной транзакционной БД — распределённые транзакции между сервисами на этом масштабе себя не окупают.

Кандидаты на вынос в отдельные сервисы уже на старте (совпадают с тем, что и так нужно для первой вертикали — маркетплейса):

| Сервис | Почему выносится сразу | Протокол внутрь ядра |
|---|---|---|
| **Payment** | Отдельный периметр безопасности, идемпотентность вебхуков провайдера, цена ошибки высокая | gRPC |
| **Notification** | Асинхронный по природе, зависит от нестабильных внешних API (Telegram, email/SMS-провайдеры) | gRPC / очередь |
| **Telegram-бот** | Свой протокол общения с Telegram, часто меняется независимо от ядра, по сути просто ещё один API-клиент | HTTP (как обычный клиент API) |

Отложены до появления реальной необходимости:
- Reporting/Analytics (read-модель для тяжёлых отчётов)
- Outbound webhook dispatcher (можно начать как таблица `outbox` + фоновый воркер внутри монолита)
- Auth/Billing как отдельный сервис — ❓ актуальность нужно пересмотреть, если направление на продажи (SaaS) станет активным раньше, чем ожидалось

⚠️ **Важно не делать**: не разделять сервисы **по типу бизнеса** (`barber-service`, `designer-service` и т.д.) — это воспроизводит проблему, ради решения которой затевалось единое ядро. Разница между бизнесами должна жить в данных (тип `Case` + JSON-схема), а не в инфраструктуре.

## 6. Способы подключения клиентов

1. **Старый сайт (без изменений в коде).**
   - Для живого двустороннего обмена (создание заявок, обновление статусов) в реальности требуется хотя бы минимальное изменение на стороне сайта (вызов API ядра).
   - Для переноса истории обращений — это разовый импорт/ETL (выгрузка из существующей БД/CSV), а не постоянная интеграция через API.
   - ❓ Нужно уточнить по каждому конкретному старому сайту: есть ли доступ к его коду/серверу для добавления вызова API, или только к экспортам/БД.

2. **Telegram-бот.** Бот — обычный HTTP-клиент API ядра: создаёт `Client` + `Case` в контексте конкретного тенанта.

3. **Новый сайт под контракт ядра.** Работает по опубликованному REST-контракту (OpenAPI) с первого дня.

## 7. Платежи (в рамках MVP)

- ✅ На старте деньги идут **мимо системы** — оплата происходит вне ядра (например, напрямую через эквайринг бизнеса или наличными), ядро только **фиксирует факт и статус транзакции**.
- Модуль `Payment` в MVP отвечает за приём подтверждения оплаты (например, вебхук от провайдера или ручная отметка), а не за инициацию самого платежа.
- ❓ Нужно решить: когда и для какого кейса (вероятно, маркетплейс или тур) ядро начнёт само инициировать оплату через провайдера (ЮKassa/CloudPayments/Stripe), а не только фиксировать факт.

## 8. Уведомления

- ✅ Каналы на старте: **email или Telegram** — один из них обязателен, остальные каналы (SMS, push) откладываются.
- Уведомление клиенту (заявка принята/статус изменился) и уведомление бизнесу (новая заявка) — общая инфраструктура рассылки, разная логика адресации.

## 9. Статус-дашборд

- ✅ Дашборд — **для конечного клиента бизнеса** (человек, который заказал/записался), а не для самого бизнеса.
- ⚠️ **Рекомендация**: не строить полноценную систему аккаунтов ради этого. Использовать паттерн "трекинг по коду заказа + телефон/email" (аналог отслеживания посылки) — без регистрации.
- ⚠️ Технически — не отдельное большое приложение, а лёгкая веб-страница/виджет поверх того же API, встраиваемая в сайт бизнеса или открываемая по ссылке из Telegram-бота.

## 10. Мобильный интерфейс

- ✅ Мобильный интерфейс входит в MVP.
- ⚠️ **Рабочее допущение (требует подтверждения командой)**: раз дашборд — для конечного клиента, мобильный CRUD-интерфейс тоже, вероятнее всего, адресован конечному клиенту бизнеса (посмотреть статус, оформить заказ/запись), а не самому бизнесу. Если это не так — часть решений ниже нужно пересмотреть.
- ✅ Протокол наружу для мобилки — **HTTP** (не gRPC); gRPC используется только для внутреннего общения между сервисами ядра.

## 11. Взаимодействие между сервисами

- ⚠️ **Рекомендация**: асинхронное общение через брокер сообщений для Payment и Notification (событие не теряется, если сервис-получатель временно недоступен), а не только прямые синхронные вызовы.
- ⚠️ **Рекомендация по брокеру**: RabbitMQ, а не Kafka — проще в эксплуатации для команды без выделенного DevOps, для текущих объёмов достаточно с запасом.
- ❓ Нужна ли единая шина доменных событий ("заказ создан", "оплата прошла") для нескольких подписчиков сразу, или пока прямые связи между конкретными парами сервисов.

## 12. Надёжность и эксплуатация

С учётом того, что архитектура централизованная (одно ядро на всех тенантов, в отличие от, например, RKeeper, где касса работает локально на точке) — падение ядра затрагивает сразу всех клиентов. Практические меры, реалистичные для команды без выделенного DevOps:

- Health-check + автоперезапуск сервиса (даже простой restart policy в Docker/systemd + внешний мониторинг доступности).
- Регулярные бэкапы БД с проверенным восстановлением.
- Идемпотентный API приёма заявок (см. п.4).
- Очередь/outbox для исходящих уведомлений сайтам-клиентам — событие не теряется при временной недоступности получателя.
- Логи и алерты, чтобы о падении узнавали раньше, чем от клиента.

Цель — не "никогда не падать", а не терять данные и быстро восстанавливаться.

## 14. Стратегия реализации (рекомендация)

Учитывая размер команды (2 middle-разработчика + вайбкодинг-фронт) и отсутствие подтверждённого опыта эксплуатации микросервисов с брокером и gRPC в проде, предлагается не строить инфраструктуру в вакууме, а прогонять её через синтетический эталонный сценарий:

1. **"Tenant Zero"** — фиктивный тестовый бизнес с ненастоящими данными. Через него прогоняется весь путь: заявка → Core → Payment (тестовый режим провайдера) → Notification → статус виден в дашборде по коду заказа.
2. Это даёт рабочую, проверенную end-to-end инфраструктуру ещё до первого реального клиента — не разрозненные сервисы, ни разу не вызванные вместе.
3. Когда появится реальный клиент — подключаются реальные данные вместо синтетических, без отладки интеграции "в первый раз" на живом бизнесе.
4. Параллельно — маркетплейс как первая вертикаль для проверки доменной модели на реальном (или близком к реальному) сценарии, барбер — как вторая, структурно другая вертикаль для проверки универсальности `Case`.

## 15. Открытые вопросы, требующие ответа до/в процессе разработки

- ❓ Хостинг: единый провайдер под ядро и под дочерние сайты, или разные? Конкретный провайдер не выбран.
- ❓ Домены клиентских сайтов: свои домены у каждого бизнеса или поддомены платформы?
- ❓ Бухучёт/статистика: для платформы (учёт доходов от клиентов) или для самих бизнесов (барбер видит свою выручку)? Не решено.
- ❓ Company Profile (лого, адрес, контакты): кто и как редактирует — личный кабинет бизнеса или ручное внесение при внедрении?
- ❓ SaaS/биллинг: направление на продажи подтверждено, но модель монетизации (подписка, разовая оплата, процент с оборота) не определена; момент, когда это понадобится, не оценён.
- ❓ Мобильный интерфейс: подтвердить аудиторию (конечный клиент бизнеса, согласно текущему допущению, п.10).
- ❓ Дедлайн: конкретной даты для первого реального клиента нет — учитывать при планировании нагрузки на инфраструктурную часть.
