# ADR-0003: RabbitMQ с начала разработки, публикация через outbox

**Дата**: 2026-09-23
**Статус**: accepted
**Участники**: команда проекта
**Требования ТЗ**: ТР-13.1, ТР-13.2, ТР-14.4, ТР-15.6, issue #6

## Контекст

Ядро передаёт события в `Payment` и `Notification`. ТР-14.4 запрещает терять события, когда получатель недоступен. Проект учебный (п. 3.3 ТЗ), поэтому команда сознательно берёт брокер сразу, а не откладывает его.

## Решение

Ядро общается с `Payment` и `Notification` асинхронно через RabbitMQ. Событие сначала пишется в таблицу `outbox` в той же транзакции, что и данные, а фоновый обработчик публикует его в брокер. Получатели обрабатывают события идемпотентно.

## Рассмотренные альтернативы

### Только outbox и gRPC, без брокера
- **Плюсы**: меньше инфраструктуры.
- **Минусы**: нет опыта работы с брокером; каждый новый получатель — новый прямой вызов.
- **Почему нет**: проект учебный, опыт с брокером — одна из целей.

### Kafka
- **Плюсы**: хранит историю событий, выдерживает большой поток.
- **Минусы**: заметно сложнее в эксплуатации.
- **Почему нет**: такие объёмы не ожидаются (ТР-13.2).

### Публиковать в брокер прямо из бизнес-кода, без outbox
- **Почему нет**: при сбое между записью в БД и отправкой в брокер событие теряется, а это нарушает ТР-14.4.

## Последствия

### Положительные
- События не теряются ни при падении получателя, ни при падении брокера.
- Новые получатели подписываются на события без изменения ядра.

### Отрицательные
- Появляются ещё один компонент для запуска и мониторинга и доставка «хотя бы один раз» (at-least-once): получатели обязаны отсеивать дубли.

### Риски
- **Получатель обработает событие дважды.** Снижается идемпотентной обработкой по идентификатору события.
