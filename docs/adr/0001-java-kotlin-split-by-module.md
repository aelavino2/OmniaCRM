# ADR-0001: Разделение Java и Kotlin по модулям

**Дата**: 2026-09-23
**Статус**: accepted
**Участники**: команда проекта (оба backend-разработчика)
**Требования ТЗ**: REQ-15.1, REQ-7.1, REQ-7.2

## Контекст

REQ-15.1 фиксирует стек «Kotlin/Java, Spring Boot», но не говорит, где какой язык. Команда — два разработчика, и оба хотят писать на разных языках. Если смешивать Java и Kotlin без правил, непонятно, кто за что отвечает, в одном модуле нужны две настройки компилятора, а общий код размывает границы сервисов.

Ядро (`core`) — самая большая часть и сильнее всего завязано на JPA. Payment, Notification и Telegram-бот — небольшие отдельные сервисы (REQ-7.2).

## Решение

Язык выбирается **на весь Gradle-модуль**, граница языков совпадает с границей сервисов:

| Модуль | Язык |
|---|---|
| `core` (Tenant, Client, Case, Catalog, Outbox) | Java |
| `payment` | Kotlin |
| `notification` | Kotlin |
| `telegram-bot` | Kotlin |
| `contracts` (OpenAPI, `.proto`) | без языка, код генерируется в каждом модуле |
| Скрипты сборки | Kotlin DSL (`*.gradle.kts`) |

Правила:

1. Один модуль — один язык, включая тесты.
2. Общего кода между модулями нет, кроме сгенерированного из `contracts`. Модули общаются только по сети (REST, gRPC, брокер сообщений).
3. Каждый PR проверяет второй разработчик, в том числе на «чужом» языке.
4. В Kotlin-модулях подключены `kotlin("plugin.spring")` и `jvmToolchain(25)`; при использовании JPA — ещё `kotlin("plugin.jpa")`.

## Рассмотренные альтернативы

### Java в `core` и `payment`, Kotlin в `notification` и `telegram-bot`
- **Плюсы**: Payment пишется в той же технологии, что и ядро, с которым он теснее всего связан.
- **Минусы**: около 70% объёма ложится на одного разработчика.
- **Почему нет**: сильный перекос нагрузки; у Kotlin-разработчика остаются только периферийные сервисы.

### Kotlin в `core`
- **Плюсы**: компактнее код, защита от `null`.
- **Минусы**: JPA рассчитан на Java-классы; в Kotlin нужны `all-open` и `no-arg`, а `data class` в роли сущности ломает `equals`/`hashCode` и ленивую загрузку.
- **Почему нет**: самый большой модуль получил бы больше всего подводных камней.

### Смешивать языки внутри модулей
- **Плюсы**: полная свобода.
- **Минусы**: нет владельца кода, сложнее сборка и ревью.
- **Почему нет**: для команды из двух человек ясность важнее гибкости.

## Последствия

### Положительные
- Каждый понимает, где его зона, при этом работа идёт параллельно: ядро на Java, сервисы на Kotlin на заглушках контракта.
- Payment получает `sealed`-классы для состояний платежа и защиту от `null`, Notification и бот — корутины для работы с внешними API.
- Контракт между языками — только `contracts`, поэтому границы сервисов не размываются.

### Отрицательные
- Обоим нужно читать оба языка ради перекрёстного ревью.
- Инструменты двойные: два набора правил ревью, агентов и навыков, два стиля тестов.

### Риски
- **Каждый знает только свою половину.** Снижается обязательным перекрёстным ревью (правило 3).
- **Ядро — критический путь.** Если оно отстанет, Kotlin-сервисам нечего вызывать. Снижается тем, что контракты пишутся до кода (ADR-0004), а сервисы — на заглушках контракта.
