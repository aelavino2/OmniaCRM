## 1. Общие положения

ТЗ — источник правды по архитектуре, доменной модели и контрактам. При расхождении с другими материалами проекта, включая `README.md`, прав ТЗ.

### 1.1. Статусы требований

Каждому требованию настоящего ТЗ присвоен один из трёх статусов. Статус определяет порядок применения требования и приведён непосредственно в его заголовке.

| Статус | Определение | Порядок применения |
|---|---|---|
| **УТВЕРЖДЕНО** | Решение принято командой проекта | Требование обязательно к исполнению. Отступление допускается только после изменения ТЗ |
| **НА СОГЛАСОВАНИИ** | Предложение, не подтверждённое командой проекта | Требование не подлежит реализации как принятое решение и не может закладываться в проектные решения как данность. До начала соответствующих работ требование подлежит явному подтверждению либо отклонению |
| **НЕ ОПРЕДЕЛЕНО** | Решение отсутствует | Решение не принимается исполнителем единолично. Вопрос выносится на обсуждение с командой проекта. Перечень таких вопросов приведён в разделе 17 |

Наиболее вероятная ошибка при работе с настоящим документом — трактовка требования со статусом НА СОГЛАСОВАНИИ как утверждённого. Подтверждения не получило требование REQ-16.1.

Статус НА СОГЛАСОВАНИИ меняется на УТВЕРЖДЕНО только по итогам обсуждения с командой. При любом изменении требования обновляется таблица трассировки (раздел 18).

### 1.2. Идентификация требований

Требования обозначаются **REQ-<номер раздела>.<порядковый номер>**, неопределённые вопросы — **OQ-<порядковый номер>**. Идентификатор закреплён за требованием навсегда и после удаления требования не переиспользуется.

Идентификаторы — английские аббревиатуры: REQ — requirement (требование), OQ — open question (открытый вопрос). У каждого требования и открытого вопроса есть постоянный якорь: `#req-15-7` для REQ-15.7, `#oq-10` для OQ-10. Из issues на требование ссылаются по якорю, например `docs/terms-of-reference.md#req-15-7`. Якорь не зависит от заголовка и статуса требования, поэтому ссылка не ломается при их изменении.

## 2. Термины и определения

| Термин | Определение |
|---|---|
| **Ядро** | Совокупность компонентов системы, реализующих работу с сущностями «Тенант», «Клиент» и «Дело» и использующих единую транзакционную базу данных |
| **Тенант** (Tenant, Project) | Логический контейнер, обеспечивающий разделение данных различных бизнесов в пределах одной инсталляции системы |
| **Клиент** (Client) | Физическое лицо — потребитель услуг бизнеса, подключённого к системе. Доступа к системе не имеет и взаимодействует с ней только через клиентскую систему бизнеса. Не следует смешивать с понятием «клиентская система» |
| **Владелец бизнеса** | Пользователь системы: владелец подключённого бизнеса. Единственная категория лиц, работающая с системой напрямую |
| **Клиентская система** | Сайт бизнеса либо Telegram-бот, подключённые к системе и передающие в неё обращения клиентов через прикладной программный интерфейс |
| **Дело** (Case, Order) | Универсальная сущность, описывающая обращение клиента: запись на приём, заявку, заказ товара либо бронирование |
| **Тип дела** | Классификационный признак дела, определяющий применимую к нему схему данных и правила валидации |
| **Платёж** (Payment) | Запись о факте и статусе оплаты по делу |
| **Уведомление** (Notification) | Сообщение, направляемое клиенту либо бизнесу при наступлении значимого события |
| **Профиль компании** (Company Profile) | Совокупность динамических данных бизнеса: наименование, адрес, контактные данные, логотип, режим работы |
| **Вертикаль** | Отдельный бизнес-кейс, реализуемый средствами системы (барбершоп, дизайнер интерьеров, туристический сайт, маркетплейс) |
| **Tenant Zero** | Синтетический тестовый тенант с недостоверными данными, используемый для сквозной проверки работоспособности системы |
| **Вайбкодинг** | Принятая в проекте модель разработки пользовательского интерфейса силами ИИ-инструментов без выделенного frontend-инженера |

## 3. Назначение, цели и условия разработки

### 3.1. Назначение системы

Система предназначена для централизованной обработки обращений клиентов, поступающих из разнородных клиентских систем различных бизнесов, а также для хранения сведений о клиентах, состоянии их обращений и связанных с ними платежей.

Логика работы с клиентами, обращениями и уведомлениями реализуется в системе однократно и переиспользуется всеми подключёнными бизнесами, что исключает её повторную реализацию в каждом новом проекте.

### 3.2. Цели создания системы

1. Обеспечить подключение нового бизнеса к системе в сжатые сроки без доработки схемы данных и архитектуры.
2. Обеспечить хранение данных различных бизнесов без их смешения.
3. Обеспечить единообразие контракта приёма обращений для всех типов клиентских систем.

### 3.3. Условия разработки

| Условие | Значение | Статус |
|---|---|---|
| Характер проекта | Инициативная разработка с перспективой коммерциализации. Внешнее финансирование отсутствует, внешний директивный срок не установлен | УТВЕРЖДЕНО |
| Учебная цель | Проект одновременно служит развитию навыков команды. Поэтому допускается инфраструктура сверх минимально необходимой (брокер сообщений, gRPC, отдельные сервисы), если она не нарушает остальные требования | УТВЕРЖДЕНО |
| Мотивация разработки | Подготовка системы до появления реального заказчика из числа заинтересованных лиц (барбершоп, дизайнер интерьеров, туристический сайт, маркетплейс) с целью последующего подключения заказчика в сжатые сроки | УТВЕРЖДЕНО |
| Состав команды | Два backend-разработчика квалификации middle, включая автора идеи. Разработка пользовательского интерфейса — по модели вайбкодинга, без выделенного frontend-инженера | УТВЕРЖДЕНО |
| Срок завершения | Не установлен. См. OQ-7 | НЕ ОПРЕДЕЛЕНО |

## 4. Границы охвата

### <a id="req-4-1"></a>REQ-4.1. Поддерживаемые бизнес-кейсы — УТВЕРЖДЕНО

Система должна обеспечивать функционирование четырёх бизнес-кейсов:

1. барбершоп — запись клиента на определённое время;
2. дизайнер интерьеров — заявка на консультацию;
3. туристический сайт — бронирование с оплатой;
4. маркетплейс изделий — заказ товара с оплатой.

### <a id="req-4-2"></a>REQ-4.2. Поддерживаемые способы подключения — УТВЕРЖДЕНО

Система должна обеспечивать подключение клиентских систем тремя способами:

1. существующий сайт без внесения изменений в его код;
2. Telegram-бот;
3. новый сайт, спроектированный под контракт системы.

Детализация способов подключения приведена в разделе 8.

### <a id="req-4-3"></a>REQ-4.3. Порядок вертикалей — УТВЕРЖДЕНО

Порядок реализации вертикалей не фиксируется. Ядро обязано работать для любого из бизнес-кейсов REQ-4.1, с какого бы из них ни началось подключение. Абстракция дела считается проверенной после работы как минимум на двух структурно различных вертикалях (например, запись на время и онлайн-заказ).

### <a id="req-4-4"></a>REQ-4.4. Пользователи системы — УТВЕРЖДЕНО

Напрямую с системой работают только владельцы бизнеса: просматривают и ведут обращения, клиентов и статистику. Клиенты бизнеса доступа к системе не имеют — ни к дашбордам, ни к обращениям. Клиент записывается или оформляет заказ одним из двух способов: через сайт бизнеса, подключённый к системе, либо через Telegram-бот.

## 5. Требования к архитектуре, фиксируемые с начала разработки

Требования настоящего раздела реализуются с начала разработки. Их реализация на раннем этапе не требует существенных затрат, тогда как внесение соответствующих изменений на последующих этапах сопряжено с переработкой схемы данных и контрактов.

Программный код, нарушающий требования настоящего раздела, считается не соответствующим ТЗ независимо от его работоспособности.

### <a id="req-5-1"></a>REQ-5.1. Мультитенантность — УТВЕРЖДЕНО

Каждая таблица базы данных должна содержать атрибут `tenant_id` с момента создания схемы, в том числе в период, когда в промышленной эксплуатации находится единственный тенант.

Введение атрибута после появления второго тенанта не допускается.

### <a id="req-5-2"></a>REQ-5.2. Гибкая схема дела — УТВЕРЖДЕНО

Сущность «Дело» не должна содержать полей, определённых под конкретный бизнес-кейс. Состав атрибутов дела определяется типизированным полем формата JSONB СУБД PostgreSQL; валидация содержимого поля выполняется на уровне приложения в соответствии со схемой, установленной для каждого типа дела.

Создание отдельных таблиц либо отдельных колонок под конкретный бизнес-кейс не допускается.

### <a id="req-5-3"></a>REQ-5.3. Версионирование прикладного программного интерфейса — УТВЕРЖДЕНО

Версионирование интерфейса вводится с первой опубликованной версии. Адресация ресурсов имеет вид `/api/v1/...`.

### <a id="req-5-4"></a>REQ-5.4. Идемпотентность создания обращения — УТВЕРЖДЕНО

Операция создания обращения должна быть идемпотентной с момента её первой реализации. Повторный запрос клиентской системы не должен приводить к созданию дубликата обращения.

### <a id="req-5-5"></a>REQ-5.5. Разделение внешнего и внутреннего протоколов — УТВЕРЖДЕНО

Взаимодействие системы с внешними потребителями — сайтами и ботами бизнеса, а также веб- и мобильным интерфейсом владельца бизнеса — осуществляется по протоколу HTTP с применением архитектурного стиля REST.

Взаимодействие внутренних сервисов системы между собой осуществляется по протоколу gRPC.

Мобильный клиент относится к внешним потребителям и использует HTTP, а не gRPC.

## 6. Требования к доменной модели

### <a id="req-6-1"></a>REQ-6.1. Состав сущностей — УТВЕРЖДЕНО

Доменная модель ядра включает следующие сущности, выделенные по результатам анализа всех четырёх бизнес-кейсов.

| Сущность | Назначение | Примечание | Статус |
|---|---|---|---|
| **Tenant / Project** | Разделение данных различных бизнесов | Обязательна с начала разработки, в том числе при единственном тенанте. См. REQ-5.1 | УТВЕРЖДЕНО |
| **Client** | Контактные данные клиента бизнеса и история его обращений | Применяется во всех бизнес-кейсах | УТВЕРЖДЕНО |
| **Case / Order** | Обращение клиента: запись, заявка, заказ, бронирование | Реализуется без полей, определённых под конкретный бизнес. См. REQ-5.2 | УТВЕРЖДЕНО |
| **Payment** | Факт и статус оплаты | Опциональный модуль. Применяется не во всех бизнес-кейсах: барбершоп и дизайнер интерьеров могут эксплуатироваться без него | УТВЕРЖДЕНО |
| **Product / Service** | Товар либо услуга в составе каталога | Применяется в бизнес-кейсах, предусматривающих каталог: маркетплейс, туристический сайт | УТВЕРЖДЕНО |
| **Status / Workflow** | Состояние дела и переходы между состояниями | На начальном этапе допускается реализация фиксированным перечислением при условии, что последующее изменение состава состояний не требует существенных затрат | УТВЕРЖДЕНО |
| **Notification** | Уведомление клиенту и (или) бизнесу | Каналы доставки установлены разделом 10 | УТВЕРЖДЕНО |
| **Company Profile** | Динамические данные бизнеса: адрес, контактные данные, логотип, режим работы | Субъект и способ редактирования не определены. См. OQ-4 | НЕ ОПРЕДЕЛЕНО |

## 7. Требования к составу и компонентам системы

### <a id="req-7-1"></a>REQ-7.1. Состав ядра — УТВЕРЖДЕНО

Компоненты, реализующие работу с сущностями `Tenant`, `Client` и `Case`, реализуются единым модулем (сервисом) с единой транзакционной базой данных.

Обоснование: применение распределённых транзакций между отдельными сервисами при предполагаемом масштабе эксплуатации не оправдано соотношением затрат и получаемого результата.

### <a id="req-7-2"></a>REQ-7.2. Состав выделяемых сервисов — УТВЕРЖДЕНО

Выделению в отдельные сервисы с начала разработки подлежат компоненты, приведённые в таблице.

| Сервис | Основание выделения | Протокол взаимодействия с ядром |
|---|---|---|
| **Payment** | Сбор данных об оплатах с сайтов бизнеса и из банка бизнеса (REQ-9.2). Обособленный периметр безопасности: доступ к банковским данным бизнеса; идемпотентность обработки входящих сообщений об оплате; высокая цена ошибки | gRPC |
| **Notification** | Асинхронный характер обработки; зависимость от внешних интерфейсов с неустойчивой доступностью (Telegram, провайдеры электронной почты и SMS) | gRPC либо очередь сообщений |
| **Telegram-бот** | Обособленный протокол взаимодействия с Telegram; независимый от ядра цикл изменений. По существу является рядовым потребителем интерфейса ядра | HTTP |

### <a id="req-7-3"></a>REQ-7.3. Компоненты, реализация которых отложена — УТВЕРЖДЕНО

Реализация перечисленных компонентов откладывается до возникновения подтверждённой потребности:

1. подсистема отчётности и аналитики (модель чтения для ресурсоёмких отчётов);
2. обособленный диспетчер исходящих вебхуков; на начальном этапе реализуется таблицей `outbox` и фоновым обработчиком в составе ядра;
3. подсистемы аутентификации и биллинга в виде отдельного сервиса. Актуальность настоящего пункта подлежит пересмотру в случае, если коммерциализация системы начнётся ранее предполагаемого срока. См. OQ-5.

### <a id="req-7-4"></a>REQ-7.4. Запрет разделения сервисов по типу бизнеса — УТВЕРЖДЕНО

Разделение системы на сервисы по признаку типа бизнеса (`barber-service`, `designer-service` и аналогичные) не допускается.

Обоснование: такое разделение воспроизводит проблему, для устранения которой создаётся единое ядро. Различия между бизнесами реализуются средствами данных — типом дела и соответствующей ему схемой JSON, — но не средствами инфраструктуры.

## 8. Требования к способам подключения клиентских систем

### <a id="req-8-1"></a>REQ-8.1. Подключение существующего сайта — УТВЕРЖДЕНО

Двусторонний обмен данными в режиме реального времени (создание обращений, получение сведений об изменении состояния) требует внесения в код существующего сайта изменений в объёме, минимально достаточном для вызова интерфейса системы. Подключение существующего сайта полностью без изменения его кода технически не обеспечивается.

Перенос истории обращений осуществляется разовой процедурой импорта данных из существующей базы данных либо из файлов формата CSV и постоянной интеграцией не является.

Наличие доступа к коду и серверу конкретного существующего сайта подлежит уточнению отдельно по каждому такому сайту. См. OQ-8.

### <a id="req-8-2"></a>REQ-8.2. Подключение Telegram-бота — УТВЕРЖДЕНО

Telegram-бот реализуется как рядовой потребитель интерфейса системы по протоколу HTTP и выполняет создание сущностей `Client` и `Case` в контексте определённого тенанта.

### <a id="req-8-3"></a>REQ-8.3. Подключение нового сайта — УТВЕРЖДЕНО

Новый сайт взаимодействует с системой в соответствии с опубликованным контрактом REST, оформленным спецификацией OpenAPI, начиная с первой версии интерфейса.

### <a id="req-8-4"></a>REQ-8.4. Независимость от технологий сайта — УТВЕРЖДЕНО

Подключение не зависит от технологий, на которых написан сайт бизнеса (PHP, C# и любые другие). Сайт взаимодействует с системой только через HTTP-интерфейс по опубликованному контракту (REQ-8.3); библиотеки под конкретный язык сайта не требуются.

### <a id="req-8-5"></a>REQ-8.5. Направление обмена — УТВЕРЖДЕНО

Сайт и Telegram-бот передают в систему заявки. Сведения о состоянии заявки клиенту через сайт не отдаются; клиент узнаёт о ходе заявки только из сообщений (раздел 10).

### <a id="req-8-6"></a>REQ-8.6. Обязательный контакт клиента — УТВЕРЖДЕНО

Заявка принимается только при наличии хотя бы одного контакта клиента: телефона, Telegram либо иного способа связи.

### <a id="req-8-7"></a>REQ-8.7. Статистика новых клиентов — УТВЕРЖДЕНО

Регистрацией считается первое обращение клиента к бизнесу (запись через сайт, Telegram-бот либо вручную владельцем). Система ведёт статистику новых клиентов отдельно по каждому бизнесу; бизнес видит только своих клиентов (REQ-5.1). Сотрудники бизнеса, работающие в системе, в эту статистику не входят.

### <a id="req-8-8"></a>REQ-8.8. Подключение и настройка бизнеса — УТВЕРЖДЕНО

Подключение бизнеса и его настройку (тенант, типы дел, профиль компании, интеграция с сайтом) выполняют разработчики платформы при внедрении. Самостоятельная настройка владельцем не предусматривается. Вопрос OQ-4 закрыт.

## 9. Требования к подсистеме платежей

### <a id="req-9-1"></a>REQ-9.1. Порядок движения денежных средств — УТВЕРЖДЕНО

Денежные средства через систему не проходят. Приём оплаты реализуется индивидуально для каждого бизнеса: онлайн-оплатой на сайте самого бизнеса либо лично (например, барбершоп получает оплату после услуги). Система в движении денежных средств не участвует.

### <a id="req-9-2"></a>REQ-9.2. Функции модуля Payment — УТВЕРЖДЕНО

Модуль `Payment` собирает данные об оплатах, не участвуя в движении денег. Источники:

1. сайт бизнеса — сообщает об оплате через интерфейс системы;
2. банк бизнеса — система получает сведения об операциях напрямую из банка владельца. Подключается позже, банк за банком под конкретного заказчика; механизм — OQ-11;
3. ручная отметка владельца — например, оплата наличными после услуги.

Повторное сообщение об одной и той же оплате не учитывается дважды.

### <a id="req-9-3"></a>REQ-9.3. Инициация платежа системой — УТВЕРЖДЕНО

Система не инициирует платежи. Онлайн-оплата, если она нужна бизнесу, реализуется на его сайте, а не в системе. Вопрос OQ-9 закрыт.

## 10. Требования к подсистеме уведомлений

### <a id="req-10-1"></a>REQ-10.1. Каналы доставки — УТВЕРЖДЕНО

На начальном этапе обеспечиваются каналы доставки «электронная почта» и «Telegram»; реализация хотя бы одного из них обязательна. Реализация каналов SMS и push-уведомлений откладывается.

### <a id="req-10-2"></a>REQ-10.2. Адресаты уведомлений — УТВЕРЖДЕНО

Подсистема обеспечивает доставку уведомлений двум категориям адресатов:

1. клиенту — о приёме обращения и об изменении его состояния;
2. бизнесу — о поступлении нового обращения.

Инфраструктура рассылки для обеих категорий общая, логика определения адресата — различная.

### <a id="req-10-3"></a>REQ-10.3. Сообщения клиенту по шаблонам владельца — УТВЕРЖДЕНО

Тексты сообщений клиенту владелец бизнеса настраивает в системе сам; рассылку выполняет система. Канал «на телефон» при отсутствии у клиента Telegram — см. OQ-13.

### <a id="req-10-4"></a>REQ-10.4. Напоминания владельцу — УТВЕРЖДЕНО

Система напоминает владельцу о предстоящих записях.

## 11. Требования к интерфейсу владельца бизнеса

REQ-11.1 — REQ-11.3 (статус-дашборд для клиента) исключены 23.09.2026: клиенты бизнеса доступа к системе не имеют (REQ-4.4). Идентификаторы не переиспользуются.

### <a id="req-11-4"></a>REQ-11.4. Вход через админ-панель сайта — УТВЕРЖДЕНО

Владелец входит в систему из админ-панели своего сайта без отдельного логина: учётная запись администратора сайта является входом в систему. У одного бизнеса может быть несколько пользователей; каждый видит только данные своего бизнеса. Механизм — одноразовая подписанная ссылка: сервер сайта запрашивает у системы ссылку для входа конкретного пользователя, передавая секретный ключ бизнеса; ссылка действует короткое время и используется один раз. Реализуется одним HTTP-запросом на любом стеке сайта (REQ-8.4). Вопрос OQ-12 закрыт.

### <a id="req-11-5"></a>REQ-11.5. Доска обращений — УТВЕРЖДЕНО

Обращения отображаются по колонкам состояний. Владелец меняет состояние переносом между колонками либо отметкой (например, «опоздал», «не пришёл»). Набор состояний задаётся типом дела (REQ-6.1).

### <a id="req-11-6"></a>REQ-11.6. Ручное создание обращения — УТВЕРЖДЕНО

Владелец создаёт обращение и клиента вручную — например, запись по телефону или клиента, пришедшего без записи.

### <a id="req-11-7"></a>REQ-11.7. Синхронизация устройств — УТВЕРЖДЕНО

Изменение, сделанное на одном устройстве (ПК, телефон), отображается на остальных без перезагрузки страницы.

### <a id="req-11-8"></a>REQ-11.8. Запись на время — УТВЕРЖДЕНО

Для типов дел с записью на время система хранит длительность и не допускает пересечения записей у одного исполнителя.

### <a id="req-11-9"></a>REQ-11.9. Статистика бизнеса — УТВЕРЖДЕНО

Статистика ведётся для самого бизнеса (вопрос OQ-3 закрыт):

1. доход за день и за месяц по данным об оплатах (REQ-9.2);
2. условный налог — процент от дохода за месяц, который задаёт владелец;
3. итоги дня («закрытие дня») — сводка за текущий день;
4. новые клиенты — число клиентов, впервые обратившихся к бизнесу (REQ-8.7).

Расчёт налога носит справочный характер и не является фискальной операцией.

### <a id="req-11-10"></a>REQ-11.10. Настраиваемая статистика — УТВЕРЖДЕНО

Владелец составляет собственные отчёты из доступных показателей.

## 12. Требования к мобильному интерфейсу

### <a id="req-12-1"></a>REQ-12.1. Состав работ — УТВЕРЖДЕНО

Мобильный интерфейс входит в объём минимально жизнеспособного продукта.

### <a id="req-12-2"></a>REQ-12.2. Аудитория — УТВЕРЖДЕНО

Мобильный интерфейс предназначен для владельца бизнеса: он видит и ведёт обращения с телефона так же, как с ПК. Клиентам бизнеса мобильный интерфейс не предоставляется (REQ-4.4). Вопрос OQ-6 закрыт.

### <a id="req-12-3"></a>REQ-12.3. Протокол взаимодействия — УТВЕРЖДЕНО

Мобильный интерфейс взаимодействует с системой по протоколу HTTP. Применение gRPC для мобильного интерфейса не допускается; gRPC применяется исключительно для взаимодействия внутренних сервисов между собой. См. REQ-5.5.

### <a id="req-12-4"></a>REQ-12.4. Форма мобильного интерфейса — УТВЕРЖДЕНО

Параллельно разрабатываются веб-дашборд и мобильное приложение на Kotlin. Оба работают через один и тот же HTTP-интерфейс системы (REQ-12.3). Вопрос OQ-14 закрыт. Платформы приложения (только Android или также iOS) — OQ-15.

---

## 13. Требования к взаимодействию между сервисами

### <a id="req-13-1"></a>REQ-13.1. Асинхронное взаимодействие — УТВЕРЖДЕНО

Взаимодействие ядра с сервисами `Payment` и `Notification` осуществляется асинхронно через брокер сообщений, а не исключительно прямыми синхронными вызовами. Брокер вводится с начала разработки. Событие публикуется через таблицу `outbox`, записываемую в одной транзакции с данными (REQ-14.4), — иначе при сбое между записью в БД и отправкой в брокер событие теряется.

Обоснование: при временной недоступности сервиса-получателя событие не утрачивается.

### <a id="req-13-2"></a>REQ-13.2. Выбор брокера сообщений — УТВЕРЖДЕНО

В качестве брокера сообщений используется RabbitMQ.

Обоснование: эксплуатация RabbitMQ требует меньших затрат по сравнению с Kafka, что существенно при отсутствии в команде выделенного инженера по эксплуатации. Производительности RabbitMQ достаточно для предполагаемых объёмов обработки с запасом.

### <a id="req-13-3"></a>REQ-13.3. Шина доменных событий — НЕ ОПРЕДЕЛЕНО

Необходимость создания единой шины доменных событий («обращение создано», «оплата произведена») с несколькими подписчиками не определена. Альтернативой является установление прямых связей между конкретными парами сервисов. См. OQ-10.

## 14. Требования к надёжности и эксплуатации

Архитектура системы является централизованной: единое ядро обслуживает всех тенантов. В отличие от систем с локальным исполнением на стороне точки обслуживания (например, RKeeper), отказ ядра затрагивает одновременно всех подключённых клиентов. Требования настоящего раздела установлены с учётом отсутствия в команде выделенного инженера по эксплуатации.

Целевым показателем является не безотказность, а сохранность данных и восстановление в приемлемый срок.

### <a id="req-14-1"></a>REQ-14.1. Контроль работоспособности — УТВЕРЖДЕНО

Система должна предоставлять интерфейс контроля работоспособности (health-check). Должен быть обеспечен автоматический перезапуск сервиса средствами политики перезапуска Docker либо systemd, а также внешний контроль доступности.

### <a id="req-14-2"></a>REQ-14.2. Резервное копирование — УТВЕРЖДЕНО

Должно быть обеспечено регулярное резервное копирование базы данных. Восстановление из резервной копии подлежит проверке.

### <a id="req-14-3"></a>REQ-14.3. Идемпотентность приёма обращений — УТВЕРЖДЕНО

См. REQ-5.4.

### <a id="req-14-4"></a>REQ-14.4. Гарантированная доставка исходящих уведомлений — УТВЕРЖДЕНО

Исходящие уведомления клиентским системам направляются через очередь либо таблицу `outbox`. Утрата события при временной недоступности получателя не допускается.

### <a id="req-14-5"></a>REQ-14.5. Журналирование и оповещение — УТВЕРЖДЕНО

Должны быть обеспечены журналирование и оповещение команды об отказах. Сведения об отказе должны поступать команде ранее, чем обращение от клиента.

## 16. Порядок реализации

### <a id="req-16-1"></a>REQ-16.1. Порядок ввода инфраструктуры в эксплуатацию — НА СОГЛАСОВАНИИ

С учётом численности команды (два разработчика квалификации middle и разработка интерфейсной части по модели вайбкодинга) и отсутствия подтверждённого опыта промышленной эксплуатации микросервисной архитектуры с брокером сообщений и gRPC инфраструктуру предлагается вводить в эксплуатацию не обособленно, а посредством её проверки на эталонном сценарии в следующем порядке:

1. **Создание тенанта Tenant Zero** — синтетического тестового бизнеса с недостоверными данными. На нём выполняется сквозной прогон полного маршрута: обращение → ядро → `Payment` (в тестовом режиме провайдера) → `Notification` → отображение обращения в интерфейсе владельца бизнеса.
2. Результатом является проверенная сквозным сценарием инфраструктура, полученная до подключения первого реального заказчика, в отличие от совокупности обособленных сервисов, ни разу не проверенных совместно.
3. При появлении реального заказчика синтетические данные заменяются реальными. Первичная отладка интеграции на действующем бизнесе исключается.
4. Порядок вертикалей не фиксируется (REQ-4.3): эталонный сценарий прогоняется как минимум для двух структурно различных вертикалей.
